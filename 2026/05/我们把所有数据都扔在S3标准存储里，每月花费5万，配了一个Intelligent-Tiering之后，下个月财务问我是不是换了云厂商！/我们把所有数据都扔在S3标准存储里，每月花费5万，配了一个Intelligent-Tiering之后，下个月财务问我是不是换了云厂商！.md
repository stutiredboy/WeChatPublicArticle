事情要从去年九月份说起。

那天下午，财务的小王拿着一张报表走到我工位旁边，指着上面一行数字问我："这个AWS的费用，每个月都是五万左右，能不能想想办法降一降？老板说了，今年降本增效是重点。"

我当时的第一反应是：五万块的云费用，业务规模摆在这里，能降到哪去？

但我还是打开了AWS Billing Dashboard，仔细看了一眼费用构成。这一看，我人直接愣住了。

S3的费用，占了总费用的将近60%。

也就是说，每个月五万块的账单里，有将近三万块花在了S3存储上。

我们是一家做内容平台的公司，用户上传的图片、视频、文档，加上每天生成的日志文件、数据备份、报表快照，所有数据全部存在S3里。三年下来，总数据量大概在150TB左右。

而这150TB的数据，全部放在S3 Standard标准存储里。

每一个字节，都在按最贵的价格计费。

先搞清楚一个事实：你的数据，80%可能根本没人访问

在动手优化之前，我先做了一件事——搞清楚这150TB数据的实际访问情况。

我用S3 Storage Lens和S3 Analytics做了一次数据分析，跑了大概两周，结果非常有意思。

过去30天内被访问过至少一次的数据，大概只有25TB左右，占总量的17%。过去90天内被访问过的数据，大概45TB，占总量的30%。过去180天内被访问过的数据，大概60TB，占总量的40%。

也就是说，有将近60%的数据，半年内没有任何人碰过。有超过80%的数据，过去一个月内没有被访问过。

这些数据包括什么呢？两年前的用户上传文件、旧版本的数据库备份、过期的日志文件、历史报表、早就下线的活动页面素材。它们安安静静地躺在S3 Standard里，每天按最贵的价格计费，但从来没人看。

这就好比你租了一个200平的大仓库，里面80%的东西你半年都没碰过，但你每个月还在按最贵的市中心仓储价格付全款。

问题找到了，接下来就是解决。

  

S3到底有哪些存储层级，价格差多少

在讲具体操作之前，有必要先把S3的存储层级理清楚。很多人用了好几年S3，其实根本不知道它有这么多层级。

以AWS美东区域（us-east-1）为例，我按照每GB每月的价格给大家做一个直观对比。

S3 Standard标准存储，每GB每月0.023美元。这是默认的存储类型，访问速度最快，适合频繁访问的热数据。

S3 Intelligent-Tiering智能分层，每GB每月0.023美元起。价格跟Standard一样甚至更低，它会自动把不常访问的数据移到更便宜的层级，稍后详细说。

S3 Standard-IA低频访问存储，每GB每月0.0125美元。价格大约是Standard的一半，适合不经常访问但需要的时候要能快速读取的数据。注意它有一个最低存储时间30天的要求，并且每次访问会额外收取检索费用。

S3 One Zone-IA单可用区低频访问存储，每GB每月0.01美元。比Standard-IA还便宜20%，区别是数据只存在一个可用区里，如果那个可用区挂了数据就没了。适合可以重新生成的数据，比如缩略图、转码后的视频等。

S3 Glacier Flexible Retrieval冰川存储，每GB每月0.0036美元。价格只有Standard的六分之一，适合归档数据。取回数据需要几分钟到几小时不等，取决于你选择的检索速度。

S3 Glacier Deep Archive深度归档存储，每GB每月0.00099美元。这是S3最便宜的存储层级，价格只有Standard的二十三分之一。取回数据需要12到48小时。适合那些法规要求你必须保留但几乎永远不会再看的数据。

看到价格差距了吗？同样是存1TB数据一个月，Standard要23.55美元，Glacier Deep Archive只要1.01美元。差了23倍。

如果你有100TB的冷数据从Standard搬到Glacier Deep Archive，每月能省多少？（23.55减1.01）乘以100，等于2254美元，折合人民币大约16000块。这只是100TB的冷数据，如果量更大，省得更多。

  

我选择了Intelligent-Tiering，原因很简单

面对这么多层级，我一开始也纠结过到底该怎么选。手动给每个对象指定存储层级？150TB的数据，几亿个对象，这不现实。用Lifecycle Policy生命周期策略按时间自动转换？可以是可以，但有个问题——有些数据虽然创建时间很久了，但偶尔还是会被访问到。如果一刀切地按时间转到Glacier，等用户访问的时候发现要等几个小时才能取回来，体验就炸了。

最终我选了S3 Intelligent-Tiering，智能分层。

Intelligent-Tiering的核心逻辑非常简单。它内部有好几个子层级：频繁访问层、不频繁访问层、归档即时访问层、归档访问层、深度归档访问层。当你把数据放进Intelligent-Tiering之后，AWS会自动监控每个对象的访问频率。如果一个对象连续30天没被访问，自动从频繁访问层移到不频繁访问层，存储成本直接降一半。如果连续90天没被访问，自动移到归档即时访问层，成本再降。如果你开启了归档访问和深度归档访问的配置，180天和270天没被访问的对象还会继续往更便宜的层级走。

最关键的是，当这些数据再次被访问时，它会自动移回频繁访问层，而且访问延迟跟Standard完全一样。用户完全无感知。

Intelligent-Tiering不收取检索费用，也没有最低存储时间的限制。唯一的额外成本是每个对象每月0.0025美元的监控和自动化费用，大约每百万个对象每月2.5美元。对于我们这种单个对象平均大小在几MB到几十MB的场景，这点监控费用跟省下来的存储费用比起来，可以忽略不计。

简单来说，Intelligent-Tiering就是一个"全自动的省钱管家"。你不需要分析每个文件的访问模式，不需要设计复杂的生命周期规则，也不用担心把活跃数据误转到Glacier导致访问出问题。把数据扔进去就行了，它帮你搞定一切。

  

具体操作步骤：我是怎么做的

接下来是最实际的部分，我把完整的操作步骤详细写出来。

第一步，分析现有数据。

在做任何改动之前，先搞清楚你的数据现状。打开S3控制台，进入你的目标存储桶，找到Metrics选项卡，查看存储桶的总容量、对象数量、存储类型分布。然后打开S3 Storage Lens，这是AWS提供的免费分析工具，它可以帮你看到账户级别和存储桶级别的存储使用情况，包括各存储类型的占比、数据增长趋势等。

如果你想更精确地知道数据的访问模式，可以在存储桶上启用S3 Analytics Storage Class Analysis。进入存储桶的Metrics页面，点击Storage Class Analysis，创建一个新的分析配置。分析范围可以选整个存储桶或者指定前缀。启用之后，大概需要等待两周左右才能拿到有意义的分析结果。分析报告会告诉你哪些数据属于频繁访问，哪些属于不频繁访问，以及建议转换到什么存储类型。

第二步，对新上传的数据直接使用Intelligent-Tiering。

这是最简单、风险最低的一步。你不需要动现有数据，只需要让以后上传的新数据默认使用Intelligent-Tiering存储类型。

方法一是在代码层面修改。如果你的应用通过AWS SDK上传文件到S3，在上传请求里加上StorageClass参数，设置为INTELLIGENT\_TIERING。以Python的boto3为例，在调用put\_object或者upload\_file的时候加上StorageClass='INTELLIGENT\_TIERING'这个参数就行了。

方法二是在S3控制台上设置存储桶的默认存储类型。不过需要注意的是，S3本身没有直接设置"默认存储类型"的功能，这需要通过你的上传逻辑来控制。

方法三是如果你用的是CloudFront加S3的架构，或者通过API Gateway和Lambda上传文件，在Lambda函数里统一修改存储类型参数即可。

第三步，为Intelligent-Tiering配置归档访问层级。

这一步很关键，但很多人忽略了。Intelligent-Tiering默认只启用了频繁访问层和不频繁访问层的自动转换。归档访问层和深度归档访问层需要你手动开启。

打开S3控制台，选择目标存储桶，进入Properties属性页面，找到Intelligent-Tiering Archive configurations这个选项，点击Create configuration创建一个新的归档配置。配置里需要设置两个关键参数：Archive Access tier的触发天数建议设为90到180天，Deep Archive Access tier的触发天数建议设为180到730天。具体天数根据你的业务场景决定。如果你的归档数据偶尔还需要访问，设长一点保险。如果确认几乎不会再访问，设短一点省钱更快。

配置好之后，Intelligent-Tiering就会自动把长期不访问的对象逐步迁移到归档层级，存储成本会进一步大幅下降。

第四步，把现有数据从Standard迁移到Intelligent-Tiering。

新数据搞定了，接下来处理已有的150TB存量数据。这里用到的就是S3 Lifecycle Policy生命周期策略。

打开S3控制台，选择目标存储桶，进入Management管理页面，点击Create lifecycle rule创建一条新的生命周期规则。规则名称随便起一个方便识别的名字，比如migrate-to-intelligent-tiering。作用范围建议选择Apply to all objects in the bucket应用到整个存储桶，或者如果你只想迁移特定前缀下的数据就指定前缀。

在规则动作里选择Transition current versions of objects between storage classes，把转换目标设为Intelligent-Tiering，转换天数设为0天。设为0天的意思是，对于所有已经存在的对象，立刻进行存储类型转换。

注意这里有一个细节。S3的生命周期策略是异步执行的，设置好之后不会立刻生效，AWS会在后台批量处理。150TB的数据完全转换完可能需要几天时间。另外，从Standard转到Intelligent-Tiering的转换操作本身会产生一点费用，大约每千次请求0.01美元。150TB按平均对象大小10MB估算大概有1500万个对象，转换费用大约150美元，这是一次性的成本。

第五步，对于明确不再需要的数据，直接设置过期删除。

在做迁移的同时，我还梳理了一遍数据，发现有不少数据其实根本不需要保留了。比如超过两年的临时日志、过期的A/B测试素材、废弃的旧版本备份文件。这些数据即使放在最便宜的Deep Archive里也是浪费钱，因为根本不会有人再去看它们。

对于这类数据，我单独创建了几条生命周期规则，针对特定前缀设置了过期删除。比如logs/前缀下的文件，创建超过365天后自动删除。temp/前缀下的文件，创建超过90天后自动删除。旧版本的备份文件，保留最近三个版本，其余自动删除。

这一步直接砍掉了大约30TB的无用数据，效果立竿见影。

第六步，启用S3 Storage Lens持续监控。

所有优化措施做完之后，不能就撒手不管了。数据是会持续增长的，今天优化好了，半年后如果不注意，可能又会回到老样子。

我在S3 Storage Lens里创建了一个Dashboard，设置了每周查看一次。重点关注几个指标：各存储类型的容量占比是否合理，数据增长趋势是否正常，Standard存储的占比是否在持续下降。如果发现Standard占比突然升高，说明可能有新的数据源没有配置Intelligent-Tiering，需要及时处理。

  

最终效果：从每月三万降到了八千

所有操作做完大概一周后，我开始在Cost Explorer里观察S3费用的变化。

第一个月因为还在转换过程中，效果还不完全。S3费用从之前的三万左右降到了两万出头。

第二个月，转换全部完成，归档层级也开始生效。S3费用降到了一万二左右。

第三个月，深度归档层级也开始起作用了，加上之前设置的过期删除规则清理掉了一批旧数据，S3费用稳定在了八千左右。

从每月三万降到八千，每月省了两万二。加上之前就在优化的其他服务，整个AWS账单从五万降到了不到一万五。

就是在第三个月的月初，财务的小王又来找我了。他拿着报表，一脸疑惑地问我："你们是不是换云服务商了？上个月费用怎么突然降了这么多？不会是哪个服务忘开了吧？"

我说没换，AWS还是那个AWS，服务一个没少，数据一字节没丢。只是给数据搬了个家，让它们住到该住的地方去了。

  

几个容易踩的坑，提前帮你避开

做这件事的过程中，我也踩了几个坑，提前分享给大家。

第一个坑是小文件不适合Intelligent-Tiering。Intelligent-Tiering对每个对象收取监控费用，每个对象每月0.0025美元。如果你的存储桶里有大量小于128KB的小文件，监控成本可能反而比省下来的存储成本还高。AWS官方也建议，小于128KB的对象不会被自动分层，它们会一直待在频繁访问层。所以如果你的数据主要是大量小文件，Intelligent-Tiering可能不是最佳选择，这种情况下用Lifecycle Policy直接按时间转Standard-IA或者Glacier可能更划算。

第二个坑是归档层级的数据访问有延迟。Intelligent-Tiering的频繁访问层和不频繁访问层访问延迟跟Standard一样，毫秒级。但如果数据被自动移到了归档访问层，再次访问时需要等待三到五个小时才能取回。如果移到了深度归档访问层，需要等12到48小时。所以在设置归档层级的天数时要慎重，不要设得太短，免得用户实际需要的数据被归档了，访问体验变差。

第三个坑是Lifecycle Policy和Intelligent-Tiering的配合要注意逻辑冲突。如果你同时设置了一条Lifecycle规则把数据在60天后转到Glacier，又配置了Intelligent-Tiering的归档层级在90天后触发，这两个策略可能会产生冲突。一般来说，Lifecycle Policy的优先级更高。建议选择一种方案作为主策略，不要两个同时用在同一批数据上。

第四个坑是跨区域复制会产生额外费用。如果你启用了S3 Cross-Region Replication跨区域复制，那么复制目标桶里的数据存储类型需要单独设置。很多人在源桶做了Intelligent-Tiering，但目标桶的复制数据还是Standard，等于省了一半又花了一半。记得在复制规则里指定目标存储类型。

  

一张清单帮你快速上手

最后，我把整个操作浓缩成一张可以直接照着做的清单。

先做数据分析。开启S3 Storage Lens和S3 Analytics，跑两周拿到数据访问报告。

然后修改上传逻辑。让新数据默认使用Intelligent-Tiering存储类型。

接着配置归档层级。在Intelligent-Tiering Archive configurations里设置归档访问层和深度归档访问层的触发天数。

再创建Lifecycle Policy。对现有Standard数据设置转换规则，目标为Intelligent-Tiering，转换天数设为0。

同时清理无用数据。对明确不再需要的数据设置过期删除规则。

最后持续监控。用S3 Storage Lens每周检查一次，用AWS Budgets设置费用告警。

整套操作不需要停服，不需要迁移数据到新的存储桶，不影响任何线上业务。一个运维工程师，一个下午就能搞定。

  

写在最后

S3的费用优化，说到底就是一句话：别让冷数据享受热数据的待遇。

这件事的技术门槛不高，真正的门槛是"意识"。大部分团队不是不知道S3有不同的存储层级，而是觉得"每个月也没多少钱""以后再说吧""万一转了有问题呢"。于是拖着拖着，冷数据越积越多，账单越来越高，等到老板追问的时候才开始动手。

我们公司150TB数据，每月从三万降到八千，一年下来省了二十六万。这笔钱，够给团队每人发一台显示器了。

而我做的事情，说白了就是在S3控制台上点了几下鼠标，配了几条规则。

如果你的公司也在用S3，今天就花十分钟打开Storage Lens看一眼。那个数字可能会让你和当初的我一样，愣在屏幕前。
