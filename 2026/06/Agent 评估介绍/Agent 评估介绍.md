# Agent Systems

LLM 具备 **Reasoning** 、**tool calling** 、Solving complex, multi-step problems，而 Agent 的独特之处在于其能在 **agentic loop** 中整合这些组件以解决复杂问题。

事实上，对智能体最简单的定义就是能在loop 中自主使用工具的LLM。与传统LLM 不同，agent 必须评估中间结果，并从自身错误中动态恢复，才能在这个agent loop 中有效运行。

## Agent 组件

一个智能体系统通常由三个部分组成：

  * 底层LLM（或推理模型）
  * Tools for the agent to use
  * Instructions for the agent

LLM 充当系统的“大脑”，判断朝着最终解决方案推进的进度，并确定为达成目标必须采取的步骤。许多情况下，要得出正确的最终解决方案，仅靠大模型本身是不够的。我们必须明确设定智能体的预期行为，并让模型在必要时能够调用工具或开展复杂推理。

## Tool use

为了与外部环境交互，大语言模型需要能够使用API、命令行界面或MCP服务器等工具。

例如，如果我们希望智能体帮我们在当地餐厅预订餐桌，只需教模型如何调用OpenTable API即可。具体来说，通过创建一组与工具调用相关的特殊标记并教LLM 如何使用这些标记，工具调用可以在LLM 的标记流中自然地处理

创建有用的工具是一门艺术，这类工具需能被智能体轻松理解并正确调用。**工具应具备完善的文档、明确的用途，与其他工具的重叠度尽可能低，且能优雅地处理错误** 。判断一款工具设计是否合理的最简单方法，就是直接问自己：一名人类工程师能否依据提供的文档使用这款工具？

LLM 可以利用工具获取外部信息，以帮助减少幻觉、完成其所处环境中的任务、执行代码、调用其他智能体等等。如果某项需要完成的任务没有可用的API，我们甚至可以依靠计算机使用原语，让智能体直接与计算机上的任意应用程序交互

### 如何评估tool calling？

用于衡量工具调用能力的完整基准测试

  * https://gorilla.cs.berkeley.edu/leaderboard.html

其性能会通过多种不同指标来衡量：

  1. 调用准确率衡量的是大语言模型是否在应该调用工具时正确地发起调用，或在不应该调用工具时成功避免调用。例如，模型可能会在本应直接回答问题的情况下调用工具。
  2. 选择准确率用于衡量大语言模型是否调用了正确的工具，通常通过跟踪包含解决特定问题所需工具列表的真实轨迹来实现。
  3. 结构准确性和模式有效性用于衡量工具调用的结构是否正确。例如，我们的模型不应在工具调用中包含错误参数，也不应提供错误的调用结构。
  4. 轨迹准确性考察模型在解决问题时调用工具的序列，并以某种方式将其与真实情况进行比较（例如，正确的调用顺序、正确的选择、使用不必要的工具等）。

我们也可以采用结果导向的评估方式，重点关注 LLM 的最终答案是否正确，而非其生成答案所使用的工具。

## Reasoning

推理在我们构建高效智能体系统的能力中也起着关键作用。尽管我们可以将标准LLM 用作智能体系统的底层模型，但**使用具备推理能力的模型通常会更有益** 。为解决多步骤任务，智能体必须能够将复杂问题拆解为更小、更简单的部分，并解决每个部分——可能需要借助工具——以得出最终解决方案。此外，**模型必须能够在解决问题的过程中进行自我反思并从自身错误中恢复** 。以这种方式处理长周期问题所需的推理水平和可靠性，直到推理模型的出现才成为可能。

推理模型不会立即给出答案，它们会在给出最终答案之前，生成一段较长的——通常是隐藏的——文本推理轨迹。这一思考过程天然适用于 inference-time scaling laws。**该模型可被训练为针对不同长度动态进行推理——通常以推理轨迹中的标记数来衡量** 。推理轨迹越长，推理时所需的计算量就越大，因为我们生成的标记数量也更多。不过，这种计算投入通常能提升模型性能，让模型花费更多时间进行推理，从而解决更难的问题。

推理模型和标准LLM可以协调工作，比如在多智能体系统中，推理模型可以用作planning 或者编排模型，普通LLM作为工具，处理简单的子任务。

## Instructions

提示的核心可取自领域现有文档（如标注指南或政策文件）。提示应尽可能清晰，通过明确规则或具体示例阐明边缘情况，并指明对智能体的具体行为要求。理想情况下，提示应在简洁性和具体性之间取得平衡。我们需要提示足够详细，以可靠地指导智能体行为，但过于复杂的提示会变得脆弱且难以维护。为了帮助为智能体编写更优的说明，我们可采用模型循环方法——即自动提示优化器——对提示进行迭代优化，提升其清晰度。

## ReAct framework

一个完整的智能体系统将所有这些组件整合在一个while循环中：这被称为agentic loop。在该循环中，智能体将根据提供的指令进行推理、调用工具并采取行动，直到根据智能体的退出条件达到终止状态。此时，智能体将放弃对工作流的控制权——要么交给人类用户，要么交给另一个智能体。整个过程被视为 agentic loop 的一次“运行”。

agentic loop 的理念很简单，但是存在诸多变体，最早变体之一是ReAct，如上图。

ReAct 智能体循环被组织为一系列连续步骤。在每一步，我们的智能体会观察环境的当前状态，推理出最佳后续步骤，并基于其推理过程采取相应行动。

ReAct 的核心创新之处在于其同时强调思考与行动。智能体循环的结构设计使得模型在决定采取正确行动时，会对每一个执行的行动进行明确推理，并考量所有上下文——例如工具调用的观察结果或先前的思考内容。简单来说，推理与行动之间存在共生关系。

# Multi-Agent Systems

我们可以通过向系统中逐步添加更多工具和条件逻辑来扩展智能体的功能，具体形式为提示模板或修改后的指令。为了让智能体表现出色，我们应为所有工具设定清晰的名称、描述和参数，并提供详细的指令，明确任务的预期操作和结果。

## When are multiple agents needed?

多智能体系统有助于从逻辑上拆分复杂任务的组件，但它们也更为复杂。因此，我们仅应在必要时扩展至多智能体系统。使用多个智能体可能带来益处的常见迹象包括：

  * 单智能体系统的指令过于冗长，即便指令逻辑清晰、格式规范，智能体也难以准确遵循。
  * 由于可用工具数量过多，智能体对工具的选择出现了错误。

## Types of multi-agent systems

  * 管理者设置：一个中央“管理者”智能体通过工具调用协调专业智能体，每个智能体负责一项特定任务或领域。
  * 去中心化设置：多个智能体根据各自的专业领域相互交接任务，以对等方的形式开展运作。

管理者设置不必将任务的所有状态都保留在单个智能体中，而是可以触发子智能体来处理任务组件。在这种设置下，我们的主智能体负责制定解决任务的高层计划并与用户交互，而子智能体则执行特定的技术任务（例如探索代码或检索信息），并将相关上下文返回给主智能体。使用子智能体有助于防止主智能体的上下文过载，从而提高系统可靠性。

去中心化多智能体系统没有用于协调任务执行的中心化智能体。相反，**控制权在多个对等运行的智能体之间传递** 。智能体通过工具调用或函数调用相互传递控制权。当我们无需中心化智能体来整合结果或与用户交互时，这种架构效果最佳。在去中心化系统中，多个不同的智能体可根据需要控制执行流程并与用户交互。例如，我们可以构建一个智能体支持系统：先由一个智能体对问题进行分类，再将控制权传递给专门的智能体来解决该特定类型的问题。

无论采用哪种方法，多智能体系统都不会显著改变构建智能体的最佳实践。我们仍然需要清晰的指令和带有高质量元数据的实用工具。不过，由于我们现在要处理多个智能体，还需要考虑系统如何随时间扩展——向系统添加新智能体不应成为负担。我们应以模块化的方式设计系统，并确保在不对其余智能体进行大量修改的情况下，就能完成向系统添加新智能体的操作。

# Context Engineering

在使用智能体时，Prompt engineering 的流程略有不同。智能体能够通过工具调用执行多种操作——例如写入文件或调用应用程序接口——这使得大语言模型的上下文窗口中可存在范围广泛的数据源

这些数据源会随着时间推移而扩展，因为智能体运行在智能体循环中。尽管现代大模型运行速度快且支持长上下文（即数百万个token），但**上下文退化 context rot** 是一个普遍存在的问题。

随着智能体上下文中标记数量的增加，模型准确回忆信息的能力会下降。因此，我们**必须主动优化智能体上下文的内容，以确保智能体持续保持良好的性能。上下文不能变得过于庞大，也不能被无关信息污染。** 这一过程通常被称为context engineering ——一种以智能体为中心的提示工程。

## Dynamic context

在使用传统大语言模型时，我们通常会将静态上下文加载到模型中。例如，检索增强生成（RAG）这类技术非常流行，它会检索信息片段并将其拼接到大语言模型的上下文窗口中。尽管检索增强生成有效，但它是一种静态方法：模型会先检索出回答问题所需的所有信息，再将这些信息添加到上下文窗口中，之后才会尝试回答问题。得益于工具调用能力，智能体**采用了一种基于逐步披露的更具动态性的方法。智能体不会预先加载所有相关上下文，而是会主动探索并动态判断何时需要新的上下文。**

为避免上下文失效，我们的智能体用于检索上下文的工具应采用令牌高效的设计方式。例如，读取文件时，智能体可以读取特定行号，或仅预览文件头部，而非始终将整个文件加载到上下文中。如果为智能体设计的工具足够合理，那么智能体就能以主动规避上下文失效的方式动态发现上下文。智能体有目的地使用工具，仅在运行时检索解决问题所需的信息。

## Compaction

与传统大语言模型（LLMs）不同，智能体需要多轮运行以解决长周期任务。在这多轮交互过程中，智能体会进行推理、调用工具、自我反思等操作，因此其上下文会快速扩展。然而，由于底层大语言模型的上下文窗口有限，我们必须开发相关技术来高效管理上下文。压缩是实现这一目标最常用的技术类别，目前存在多种形式的压缩方法：

  * 摘要生成：利用大语言模型生成长对话的摘要，并使用该更短的摘要重新初始化全新的上下文窗口。
  * 工具结果清除：移除智能体对话历史中旧工具调用的输出负载。
  * 记笔记：将笔记写入外部数据存储（例如 Markdown 文件），智能体之后可在需要时访问这些笔记。

记笔记不仅仅是一种压缩技巧——智能体即使不执行压缩，也能在解决问题的过程中保留笔记。这是一种在高效管理智能体上下文的同时提升性能的极其有效的技巧。

例如，**智能体可以创建待办事项清单来规划解决方案并跟踪进度，记录解决方案某一部分中使用的设计原则以助力未来保持一致性，或是在执行自主实验时将实验结果写入自己的实验日志** 。记笔记在执行压缩操作时也同样有用，因为智能体可以在压缩对话历史的同时，创建相关上下文的详细笔记。

没有哪一种压缩技术效果最佳，每种技术都有其自身的优势：

  * 摘要能在长时间对话中保持流畅的交流感，但在生成摘要时可能会丢失重要信息。
  * 工具清理不太可能导致关键信息丢失，但仅靠它无法确保上下文窗口不会被耗尽。
  * 记笔记能让智能体在自身语境之外存储知识，但智能体可能难以妥善利用这一外部语境。

上下文工程的核心思路很简单：移除无关上下文，保留未来需要用到的上下文。遗憾的是，预测智能体上下文中信息的未来用途难度很大，且取决于具体任务。要为压缩等方法确定最佳方案，我们必须为智能体构建可靠的基准，以真实地评估这些能力。

## 智能体支架

智能体系统是直接建立在标准 LLM 接口之上的。我们只需借助外部工具，扩展LLM 的能力，以更好地助力推理和问题解决。

不过，随着智能体能力的不断提升，围绕智能体的系统设计——工具、指令、环境、问题解决策略等——也变得愈发复杂。用于运行智能体的各类组件和框架，统称为智能体框架。

不同的智能体支架可能会对以下内容进行调整：

  * 智能体与环境的交互界面。例如，部分终端智能体可能配备用于操作终端的专用工具，而其他智能体（如上图所示的 Terminus 智能体）则可直接向终端输出按键指令——操作方式与人类类似。
  * 智能体的提示策略；例如，框架可能会指示智能体在编辑前检查文件、将问题分解为多个步骤、在完成前自查工作等。
  * 智能体可用的工具及其各自的接口——包括工具的文档以及智能体在执行每条命令后看到的输出。
  * 智能体系统的结构；例如，智能体可针对解决方案的不同部分利用子智能体或多智能体架构。
  * 智能体采用的上下文管理策略，用于在上下文窗口有限的情况下解决长期运行的问题。

### 性能影响

鉴于脚手架控制着智能体与待解决任务之间的接口，将模型性能与智能体性能解耦是困难的。性能不佳可能源于模型能力不足、脚手架设计不佳，或两者兼而有之。

在评估智能体时，我们评估的是模型与脚手架协同解决任务的能力。所使用的脚手架会对性能产生重大影响。性能较弱的模型搭配适配其特定特性的脚手架时，往往能表现得更好，反之亦然。接下来，我们将深入探讨智能体评估的各个组成部分，以及如何可靠地衡量这些系统的性能。

# 智能体评估的常见模式

智能体评估与传统用于评估大语言模型的单轮基准测试有所不同。如上所示，智能体评估需要通过多轮对话与工具和外部环境交互来完成一项任务。为开展此类长期且交互式的评估，我们必须搭建一个评估框架来管理整个端到端流程。

## 智能体评估组件

鉴于智能体可应用于各类任务，评估策略会因应用场景的不同而有所差异。不过，所有评估过程都包含一些共同的组成部分（如上所示）：

  * 该评估包含多个任务（Task），即针对智能体的、带有预定义输入和输出标准的独立测试用例。
  * 解决任务的每一次尝试都称为试验（Trial），我们通常会为每个任务执行多次试验以确保结果一致。
  * 智能体完成一次试验后，会生成一份记录（transcript）——也称为轨迹或运行轨迹，其中包含智能体在试验期间的输出、工具调用、推理步骤、中间输出或其他任何交互内容。
  * 试验完成后外部环境的最终状态被称为该试验的结果（outcome）。结果与输出不同，因为结果指的是外部环境的最终状态，而非智能体仅生成的文本。如果我们要测试智能体系统的预订能力，理想结果是预订成功。智能体可能会输出“餐厅已预订！”，但实际上并未达成这一结果。
  * 评分器（Grader）用于通过应用验证智能体记录内容或结果特定方面的检查来评估试验结果。

## 不同类型的Grader

评分员以试验的文本记录和结果为输入，并对这些资产的部分内容开展质量检查。可通过多种类型的评分员来衡量智能体的成功率，而评分员的最佳选择取决于具体应用场景。

  * 人工评估是衡量质量的权威依据，因此许多项目会先从简单的人工评估入手——例如人工检查或体验评估，这类评估会随着时间推移变得更加严格——作为第一步。然而，收集人工反馈可能难度大、成本高。
  * 自动评估技术被采用以提高实验效率。部分任务可通过确定性方式轻松验证（例如使用Python函数或某种启发式规则），而其他任务则需要开放式方法，比如LLM judge。

### Human evaluation

人工评估是智能体系统的核心标准。我们可以从简单的人工评估流程入手，由开发模型的研究人员或能快速提供反馈的内部用户进行人工检查。为此，我们需要**制定评估指南或评分标准** ，明确关键质量维度以及这些标准的评估方式（例如，采用合格/不合格或李克特量表评分）。

尽管人类评估仍是评估我们智能体系统质量的黄金标准，但我们必须长期投入大量精力来确保数据质量。

### Automatic graders

大致可分为两类：

  * Code-based可在 Python 函数中实现的启发式检查
  * Model-based基于LLM judge 的开放式检查

#### Code-based graders

基于代码的评分器示例包括对智能体结果或对话记录的字符串匹配和断言。对于数学问题，我们可以检查智能体的最终答案是否与真实答案一致，甚至可以对令牌使用量和对话轮次设定严格的上限。同样，我们可以为编码问题运行预定义的测试用例，或者检查智能体的对话记录中是否在某处调用了特定工具。还有多种传统评估指标（例如 ROUGE 或 BLEU）可供我们利用。这些都是确定性的质量检查，只需在一个基本的 Python 函数中就能轻松实现和执行。

基于代码的评分器也存在一些缺点：

  * 通常基于参考（即评分需要获取真实答案）。
  * 缺乏灵活性，可能不够细致，因此存在一定的局限性。

更具体地说，基于代码的评分器可能难以捕捉智能体行为中更多主观层面的内容。例如，检查智能体编写的代码是否能通过测试用例是客观的，而且——前提是已提供真实测试用例——这一点可以通过基于代码的评分器来完成。但判断代码是否足够简洁或优雅则具有主观性。要对这类开放式且主观的评分标准进行评估，我们需要基于模型的评分器。

#### model-based graders

基于模型的评分器原理很简单：我们只需提示 LLM 为我们评估某一质量维度。这种被称为 LLM-as-a-Judge，广泛应用于传统大语言模型和智能体系统的评估流程中。目前已有大量研究针对大语言模型评判者的最佳实践展开探索，由此衍生出几种主流的 LLM-as-a-Judge 评分方案（如下所示）

  * Pairwise \(preference\) scoring：评判者会收到一个提示和两个模型回复，并被要求找出更好的那个回复。
  * Direct assessment \(pointwise\) scoring:向评判者提供针对某一提示词的单一回复，并要求其给出评分；例如，使用 1-5 分的李克特量表。
  * Reference-guided scoring：除提示词和候选回复外，还会为评判模型提供一份标准参考回复，以辅助评分。

参考引导评分可同时适用于成对评估和直接评估两种设置。尽管这份清单并非详尽无遗，但大多数“大模型作为评判者”的评分设置都遵循这些技术的某种变体或组合。

要让 LLM-as-a-Judge 取得最佳效果，评估标准——通过 LLM 评判者的提示词传达的标准——应尽可能清晰。在近期的研究中，向 LLM 评判者提供分项评分细则进行评估的做法甚至变得流行，这类评分细则包含数十项评估标准，每项标准都由 LLM 单独进行评估。将基于模型的评估拆解为多项详细检查，再由 LLM 分别评判，能够提升评分的可靠性。

### Multiple graders

LLM judges并非完美无缺。它们具有非确定性，易受多种已知偏见影响，且比基于代码的评分者成本更高。基于这些原因，我们不应仅依赖基于模型的评分者——最好将多种评分技术结合使用。

基于代码的评分器也可用于无需基于模型评分器的更具确定性或范围较窄的检查。我们可以单独查看这些评分器的结果，但通常创建一个单一的顶级评估指标有助于简化跟踪和解读。

## 更广泛的评估类别

我们已经提及了人工评估与自动评估之间的共生关系，其中人工评估被用作校准依据。对于实际的生产系统，我们还可以采用其他几种评估方式：

  * 人工检查 or vibe checks
  * 对已报告的错误以及关键使用指标或结果进行生产监控。
  * A/B测试（即，将流量分配到多个模型变体上并比较它们的生产监控指标）
  * 明确的用户反馈；例如点赞或点踩反馈、书面评论，甚至是组织规范的用户调研。
  * 成本指标（例如，token 使用量、花费金额、速度等）。

每种方法都各有利弊。自动评估需要大量前期投入来构建评估套件，但能捕捉模型行为的开放式特征，且可随时高效执行。相比之下，生产监控或A/B测试等方法能够衡量真实用户行为，但具有被动性、耗时且结果易受干扰。最佳方案是整合所有这些方法，形成“瑞士奶酪”策略，详见下文。尽管单次评估无法发现所有错误，但增加互补评估的层级，错误流入生产环境的可能性就会降低。
